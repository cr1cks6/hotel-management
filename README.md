# Hotel Management System (Labs 3-5: JWT Security)

## 📌 Описание проекта
Серверная часть (REST API) системы управления отелем.
Проект прошел путь от простого CRUD до защищенной корпоративной системы. Реализована работа с базой данных PostgreSQL, сложная бизнес-логика транзакций и современная архитектура безопасности на основе **JSON Web Tokens (JWT)**.

---

*   **База данных:** PostgreSQL
*   **ORM:** Hibernate / Spring Data JPA

## 🔐 Архитектура безопасности (Lab 5)
Вместо стандартной Basic Auth реализована **Stateless архитектура** с парой токенов (Access + Refresh) и контролем сессий в БД.

### 1. Механизм авторизации
*   **Access Token (15 мин):** Краткоживущий токен для доступа к ресурсам API. Передается в заголовке `Authorization: Bearer <token>`.
*   **Refresh Token (30 дней):** Долгоживущий токен для получения новой пары ключей без повторного ввода пароля.

### 2. Управление сессиями (Таблица `user_sessions`)
Каждый вход в систему создает запись в БД. Это позволяет:
*   Видеть активные сессии пользователя.
*   Принудительно отзывать доступ (Revoke).
*   Контролировать использование Refresh-токенов.

### 3. Защита от взлома (Token Rotation & Reuse Detection)
Реализован механизм ротации токенов:
1.  При каждом обновлении (`/auth/refresh`) старый Refresh-токен помечается как **USED**.
2.  Выдается абсолютно новая пара токенов.
3.  Если злоумышленник попытается использовать старый (уже использованный) токен, система распознает атаку (Reuse Detection) и заблокирует всю сессию.

## 🗂 Структура Базы Данных
Система состоит из 7 таблиц:
1.  **Hotel** — Отели.
2.  **Room** — Номера (связаны с отелем).
3.  **Guest** — Гости.
4.  **Booking** — Бронирования.
5.  **Payment** — Платежи.
6.  **App_Users** — Пользователи (Login, Hash Password, Role).
7.  **User_Sessions** — Журнал сессий (Refresh Token, Status: ACTIVE/USED/REVOKED).

---

## 💼 Бизнес-операции (Logic)
Реализованы 5 сложных сценариев:

1.  **Бронирование с депозитом** (`POST /api/bookings`) — Создание брони + автоматический расчет цены + создание записи о предоплате (50%).
2.  **Умный поиск** (`GET /api/rooms/available`) — SQL-выборка свободных номеров с исключением пересечений дат.
3.  **Выселение и расчет** (`POST /api/bookings/{id}/checkout`) — Подсчет остатка долга, финальная оплата и закрытие брони.
4.  **Переселение** (`POST /api/bookings/{id}/relocate`) — Смена номера с проверкой занятости нового.
5.  **Финансовый отчет** (`GET /api/hotels/{id}/report`) — Агрегация выручки по всему отелю.

## 🚀 Инструкция по запуску и тестированию

### 1. Настройка
Задайте переменные окружения (Environment Variables) для подключения к БД:
*   `DB_USERNAME` = ваш_логин (например: `postgres`)
*   `DB_PASSWORD` = ваш_пароль

### 2. Первый запуск (Регистрация)
База данных создается пустой. Создайте пользователей через API:
*   `POST /api/auth/register` -> `{"username": "super_admin", "password": "StrongPass1!"}`
*   `POST /api/auth/register` -> `{"username": "simple_user", "password": "StrongPass1!"}`

### 3. Работа с API (Postman)
**Важно:** Basic Auth отключена. Теперь алгоритм работы следующий:

1.  **Вход (Login):**
    *   Отправьте `POST /api/auth/login` с логином и паролем.
    *   Получите `accessToken` и `refreshToken`.
2.  **Использование (Access):**
    *   Во всех запросах (создание отелей, бронирование) используйте вкладку **Auth -> Bearer Token**.
    *   Вставьте туда полученный `accessToken`.
3.  **Обновление (Refresh):**
    *   Когда Access-токен протухнет (403 Forbidden), отправьте `POST /api/auth/refresh` с вашим `refreshToken`.
    *   Получите новые токены и продолжайте работу.
