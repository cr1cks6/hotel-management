# Hotel Management System (Labs 3-4)

## Описание проекта
Серверная часть (REST API) системы управления отелем.
Проект обеспечивает полный цикл обслуживания гостей: от поиска номера и автоматического расчета стоимости до проведения платежей и формирования финансовой отчетности.

В проекте реализована **реляционная база данных (PostgreSQL)**, **сложная бизнес-логика** и **система безопасности (Spring Security)**.

---

## 🛠 Технологический стек
*   **Язык:** Java 21
*   **Фреймворк:** Spring Boot 3
*   **База данных:** PostgreSQL
*   **ORM:** Hibernate / Spring Data JPA
*   **Безопасность:** Spring Security 6 (Basic Auth)

---

## 🗂 Основные сущности (База данных)
Система состоит из 6 таблиц:
1.  **Hotel** — Отель (Название, Адрес).
2.  **Room** — Номерной фонд (Цена, Вместимость, Связь с отелем).
3.  **Guest** — Гость (ФИО, Контакты).
4.  **Booking** — Бронирование (Даты, Статус, Связь Гость-Комната).
5.  **Payment** — Финансовая транзакция (Сумма, Дата, Связь с бронью).
6.  **User** (`app_users`) — Пользователи системы для авторизации (Логин, Пароль, Роль).

---

## 💼 Реализованные бизнес-операции (Lab 3)
Реализовано 5 транзакционных операций, затрагивающих несколько таблиц:

### 1. Бронирование с депозитом
*   **Логика:** При создании брони система автоматически рассчитывает полную стоимость проживания и **мгновенно создает запись об оплате депозита (50%)** в таблице `payments`.
*   **Эндпоинт:** `POST /api/bookings`

### 2. Умный поиск свободных номеров
*   **Логика:** Сложный SQL-запрос, который фильтрует комнаты, исключая те, что заняты в указанный диапазон дат (проверка пересечений в таблице `bookings`).
*   **Эндпоинт:** `GET /api/rooms/available`

### 3. Выселение и финальный расчет (Check-out)
*   **Логика:** Система суммирует все прошлые платежи, вычисляет остаток долга, **создает финальный платеж** на разницу и закрывает бронь.
*   **Эндпоинт:** `POST /api/bookings/{id}/checkout`

### 4. Переселение гостя (Relocation)
*   **Логика:** Изменение номера в рамках активной брони с предварительной проверкой доступности нового номера.
*   **Эндпоинт:** `POST /api/bookings/{id}/relocate`

### 5. Финансовый отчет
*   **Логика:** Агрегация данных. Подсчет общей выручки и количества транзакций по всему отелю.
*   **Эндпоинт:** `GET /api/hotels/{id}/report`

## 🔒 Безопасность и Права доступа (Lab 4)
Реализована Role-Based Access Control (RBAC).

### Роли
1.  **ADMIN** — Управляющий / Кассир. Полный доступ.
2.  **USER** — Клиент. Ограниченный доступ (только просмотр и создание брони).

### Матрица доступа

| Действие | Кто может выполнять | Комментарий |
| :--- | :--- | :--- |
| **Регистрация** (`/api/auth/register`) | **ВСЕ** | Создание аккаунта. Если в имени есть "admin" — выдается роль ADMIN, иначе USER. |
| **Просмотр данных** (`GET`) | **ADMIN, USER** | Все могут смотреть список отелей, комнат и свои брони. |
| **Создание брони** (`POST`) | **ADMIN, USER** | Клиент может забронировать номер. |
| **Удаление данных** (`DELETE`) | **Только ADMIN** | Юзер не может удалять брони или отели. |
| **Изменение данных** (`PUT`) | **Только ADMIN** | Юзер не может менять параметры номеров. |
| **Бизнес-операции** (Выселение/Переселение) | **Только ADMIN** | Юзер не может сам себя выселить или переселить (это делает персонал). |
| **Управление отелем/номерами** | **Только ADMIN** | Создание отелей и комнат. |
| **Ручное создание платежа** | **Только ADMIN** | Доступ к кассе только у персонала. |

### Детали реализации
*   Пароли хранятся в базе в зашифрованном виде (**BCrypt**).
*   Пароли от базы данных вынесены в **Environment Variables** (отсутствуют в коде).
*   Включена валидация сложности пароля при регистрации.

## 🚀 Инструкция по запуску

### 1. Настройка окружения
Перед запуском в IDE необходимо задать переменные окружения (Environment Variables), чтобы скрыть чувствительные данные:
*   `DB_USERNAME` = ваш_логин_postgres (например: `postgres`)
*   `DB_PASSWORD` = ваш_пароль_postgres

### 2. Первый запуск
Так как база данных может быть пуста, необходимо создать пользователей через API регистрации:

1.  **Создать Админа:**
    *   `POST /api/auth/register`
    *   Body: `{"username": "super_admin", "password": "StrongPass1!"}`
2.  **Создать Пользователя:**
    *   `POST /api/auth/register`
    *   Body: `{"username": "simple_user", "password": "StrongPass1!"}`

Далее используйте **Basic Auth** с этими данными для проверки запросов.
